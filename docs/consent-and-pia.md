# 单独同意、PIA 与备案留痕设计

本文说明生物识别信息处理中的单独同意、隐私政策、个人信息保护影响评估（PIA）、注销封存以及可选区块链/公证备案流程。本文是工程与管理设计，正式上线前仍需由组织法务或合规人员结合实际场景复核。

## 1. 为什么需要单独同意

生物识别信息属于敏感个人信息。《中华人民共和国个人信息保护法》第二十八条将生物识别信息列为敏感个人信息；第二十九条规定，处理敏感个人信息应当取得个人的单独同意。该法第五十五条还要求，处理敏感个人信息前应进行个人信息保护影响评估并记录处理情况。

参考来源：

- 中国人大网《中华人民共和国个人信息保护法》：
  http://www.npc.gov.cn/npc/c2/c30834/202108/t20210820_313088.html

## 2. 单独同意不是长协议

单独同意不是把一句话塞进很长的用户协议，也不是默认勾选。它应当让用户在具体场景下清楚知道：

- 采集哪种生物特征；
- 为什么必须采集；
- 使用模型还是厂商 SDK；
- 原始样本和模板保存在哪里；
- 是否上云、是否备份；
- 保存多久；
- 管理员和用户分别能看到什么；
- 对个人权益有什么影响；
- 如何查询、回退、撤回、注销或封存。

## 3. 单独同意的推荐交互

可以采用“确认页/弹窗 + 独立协议 + 明确按钮”的组合。

### 推荐流程

1. 用户进入录入流程。
2. 系统展示生物识别告知页。
3. 用户可查看完整隐私政策和 SDK 说明。
4. 针对当前模态展示独立勾选项，例如：
   - “我已阅读并同意采集人脸信息用于考勤和门禁”
   - “我已阅读并同意采集指纹信息用于身份验证”
5. 用户未勾选时，确认按钮不可用。
6. 用户点击“同意并开始录入”。
7. 系统记录同意版本、时间、设备、人员和协议哈希。
8. 后续处理目的、模态、存储位置发生变化时重新取得同意。

### 多模态处理

不同模态建议分别同意，而不是一个勾选覆盖所有生物特征。例如：

- 人脸单独一项；
- 指纹单独一项；
- 虹膜单独一项；
- 声纹单独一项。

这样可以支持低配版、分特征版硬件，也符合最小必要原则。

## 4. PIA 评估内容

个人信息保护影响评估至少应覆盖：

1. 处理目的、处理方式是否合法、正当、必要。
2. 业务场景是否真的需要该生物特征。
3. 原始样本和模板的采集、存储、调用、备份、删除流程。
4. 模型、厂商 SDK、第三方服务的数据流向。
5. 对个人权益的影响及安全风险。
6. 加密、访问控制、日志审计、脱敏和备份措施。
7. 离线、在线、局域网、公网、集成、分离模式下的风险差异。
8. 离职、退租、注销后的数据封存和按需调用流程。
9. 安全事件应急预案和通知机制。

根据《个人信息保护法》第五十六条，评估内容包括处理目的和方式的合法性、正当性、必要性，对个人权益的影响及安全风险，以及保护措施是否合法、有效并与风险程度相适应；评估报告和处理情况记录至少保存三年。

## 5. 同意记录字段

建议在本地或服务端保存同意记录，不保存不必要的敏感原文。

| 字段 | 说明 |
|---|---|
| `subject` | 人员标识 |
| `modality` | 对应模态 |
| `consent_version` | 协议版本 |
| `consent_hash` | 协议文本哈希 |
| `policy` | 同意/拒绝/撤回 |
| `device_id` | 录入设备 |
| `created_at` | 同意时间 |
| `updated_at` | 状态变更时间 |
| `storage_location` | 本地/云端/混合存储 |
| `source_ip` | 可选，用于审计 |
| `record_hash` | 本条记录完整性哈希 |

## 6. 撤回同意与注销封存

用户应能查询自己的授权状态，并可按规则撤回同意。需要注意：

- 撤回不影响撤回前已发生处理的效力。
- 如果考勤、门禁、劳动管理或法定义务仍需保留数据，应说明依据和封存方式。
- 离职、退租、注销后，正常用户列表不再展示该人员。
- 数据进入注销数据区，仅保留存储、加密和经授权的按需调用。
- 具体留存年限需结合法律法规、行业规定和组织制度确定。

## 7. 区块链与公证备案

区块链可以用于增强证据链，但不能替代法定告知同意，也不建议把原始生物样本直接上链。

### 推荐上链内容

- 协议版本哈希
- 同意记录哈希
- 模板版本摘要
- 录入时间和设备标识
- 回退、注销、封存等操作哈希

### 不建议上链内容

- 原始人脸、指纹、虹膜图片
- 可还原个人身份的完整模板
- 手机号、住址、身份证号等敏感字段
- 未加密的访问日志

区块链或公证服务的作用是证明“某份协议或某条记录在某个时间已存在且未被篡改”，原始数据仍应保存在加密的本地或云端受控存储中。

## 8. 当前已提供的工程接口

核心实现位于 `biometrics/consent.py`，提供 `ConsentRepository` 和 `ConsentRecord`，支持同意、撤回、最新状态查询和历史记录查询。Web API 已提供：

- `GET /api/biometrics/consent/latest`
- `GET /api/biometrics/consent/list`
- `POST /api/biometrics/consent/grant`
- `POST /api/biometrics/consent/withdraw`

该仓库只保存协议版本、协议哈希、状态和审计字段，不保存原始生物样本或完整模板。录入 UI 接入后，应在写入 `CaptureRepository` 前确认当前模态存在有效 granted 记录。

## 9. 工程落地清单

后续实现时建议增加：

- 录入前同意页面和独立勾选控件；
- 同意记录表和状态流转；
- 协议版本号与哈希；
- PIA 模板和评估报告目录；
- 撤回、注销、封存、按需调用流程；
- 可选区块链存证适配器；
- 管理端审计页面；
- 与 `CaptureRepository` 的版本游标联动。
