总体结论

架构设计成熟度明显高于工程完成度。识别核心、云边同步与硬件抽象的抽象层和测试纪律都做得像样，但 Web 管理端的认证与门禁闭环存在 6 个 P0 级漏洞，活体检测存在 fail-open 缺陷 —— 不建议以当前状态投入生产门禁使用。

好消息是：多数问题属于「鉴权未接线」「配置未外置」类收尾工作，sync.py 中现成的 HMAC 验签实现几乎可以直接复用，按第 07 节路线图分三阶段整改即可达到可上线状态。

01

执行摘要

本次审查覆盖 biometrics/ 识别核心、sideUI/ Kiosk 边缘端、web_admin/ Flask 管理端、hardware/ 硬件层、mobile/ 移动端、tests/ 测试、部署与仓库卫生、个人信息合规 八个维度，共产出 51 条发现，全部附文件与行号级证据。

P0 致命 6 条 P1 严重 17 条 P2 一般 18 条 P3 建议 10 条 亲自复核 P0：6 / 6

三条主线贯穿全部发现：

其一，Web 端「有客户端、无服务端」。 边缘客户端同步时确实发送了 Bearer token（managers.py:2295），但服务端的 /api/face/sync* 全家、/api/agent/* 全部不做任何校验 —— 鉴权只写了一半。其中 push 端点还对匿名请求做 pickle 反序列化，构成无鉴权远程代码执行，是全项目最重的一条。

其二，门禁场景把「可用性」排在了「安全性」之前。 活体检测异常时放行（fail-open）、无 PAD 模型时降级放行并抬分、Kiosk 录入页对现场任何人开放 —— 三个缺陷叠加后，一张打印照片加十秒钟操作就可能完成「注册 + 过闸」。

其三，最好的代码恰恰没被用上。 biometrics/sync.py 的 outbox + HMAC + 幂等键 + 退避实现质量很高，但全仓库只有测试在调用它；生产同步仍走 managers.py 里的直连 HTTP。把这一模块接入生产路径，可同时消解传输明文、无验签、断网丢数据三类问题。

03

P0 致命发现

以下 6 条均已由主会话直接读取源码逐条复核，非子审查转述。任何一条未修复前，系统都不应暴露在局域网之外，更不应接入真实门禁。

P0-1Flask 会话密钥硬编码，登录可被完全绕过致命已复核 ✓
web_admin/app.py:27

源码原文：app.secret_key = 'supersecretkey'  # Change this in production。密钥随 git 分发，任何拿到代码的人可离线伪造 logged_in 会话 cookie，直接以管理员身份访问整个管理端，密码体系形同虚设。

修复：secret_key 改为环境变量注入的随机值，启动时缺失即拒绝启动；上线时作废全部旧会话。

P0-2同步端点簇完全无鉴权：任意注入、全量导出、删人、回显数据库密码致命已复核 ✓
web_admin/app.py:1628（push）· 1761（all）· 253（sync_config）· DELETE 同步端点

/api/face/sync/push 匿名即可写入 / 覆盖任意人脸记录（向人脸库注入任意人是门禁系统最直接的攻击面）；/api/face/sync/all 匿名返回全量人脸库 —— 姓名、特征向量、metadata（含身份证号、手机号字段）与人脸原图 base64，一个 GET 请求即整库拖走；/api/sync_config 直接回显 MySQL 连接配置（含 root 密码）。客户端侧 managers.py:2295 确实发送 Bearer token，但服务端从未校验 —— 防线只修了自家这一半。

修复：为上述端点统一加 token + HMAC 验签（biometrics/sync.py 已有现成实现），并按 device_id 白名单限制调用方。

P0-3无鉴权端点内 pickle 反序列化 —— 匿名远程代码执行致命已复核 ✓
web_admin/app.py:1662（位于 P0-2 的 push 端点内）

embedding = pickle.loads(base64.b64decode(embedding_b64)) —— 与 P0-2 叠加后，任何能访问该端口的人 POST 一个恶意 pickle payload 即可在服务器上执行任意代码。这是全项目风险最高的一条。

修复：改用 np.frombuffer(base64.b64decode(...), dtype=np.float32) 定长解析，彻底移除该路径上的 pickle。

P0-4Agent 工具执行面无鉴权，匿名可改写数据库与存储配置致命已复核 ✓
web_admin/app.py:262-264（认证白名单放行，注释自认「P2 再加 token 校验」）· agent_tools/tools.py:534 / 539 / 544 / 574

/api/agent/* 在全局认证中间件中被显式放行（源码注释写明「绕过 session 认证」），其下 POST /api/agent/call 与全部按工具生成的端点匿名可执行。set_config 写工具可将 MySQL / S3 指向攻击者服务器，配合 get_config 等读工具间接窃取数据；读工具无任何门槛。

修复：该执行面面向编排平台调用，应强制 Bearer token（与 P0-2 统一验签层），并在公网模式下默认关闭。

P0-5Kiosk 录入页无管理员门控 —— 现场自录人脸即可过闸致命已复核 ✓
sideUI/kiosk/app.py:287-293（仅 index 4 需管理员）· 303（录入页信号）· 447（识别通过即 unlock）

页面切换门控只拦管理页（index 4），注册页与多模态录入页对现场任何人开放。完整攻击链：走到 Kiosk 前 → 打开注册页 → 对准摄像头录一张自己的脸 → add_face → refresh_gallery → 立刻识别通过 → hardware.unlock() 开门。全程无需任何凭证，耗时以秒计。

修复：录入入口复用现成的 AdminLoginOverlay 门控；注册成功的脸不立即进入识别图库（或需管理员确认后生效）。

P0-6config.ini 明文密钥簇（未进 git，但明文落盘且可被 P0-2 间接窃取）致命已复核 ✓
config.ini [S3] / [MySQL] / [Security] / [WebAdmin] 各节

R2 对象存储的 access_key 与 secret_key、MySQL root 密码、模板加密 encryptionkey、WebAdmin token 与 salt 全部明文写在 config.ini。git 层面已核实干净：未被跟踪（.gitignore「本地配置 / 隐私」节覆盖）、对全部历史做逐值检索 0 命中 —— 没有发生仓库泄漏。但明文密钥与密文同机同目录，且 docker compose 将其挂入容器；更关键的是 P0-2 的 sync_config 端点使这些密钥可被网络请求直接读取。

修复：全部密钥立即轮换并外置（环境变量 / 密钥文件 / KMS），config.ini 仅保留非敏感项；加密密钥与密文分离存储。
